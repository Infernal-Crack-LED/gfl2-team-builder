# Front-end conventions — gfl2-team-builder

> **Class: CURRENT-STATE.** Freely rewritten when the code moves; stale content
> is deleted, not narrated.
>
> **Audience:** anyone — human or AI, any harness — writing or reviewing
> front-end code in `web/`. This doc is **binding**: where it and your instinct
> disagree, check the code, and if the code agrees with the doc, follow the doc.
>
> **Lineage:** this doc is the GFL2 instance of the nikke-sim website playbook
> (`~/nikke-sim/docs/frontend-conventions.md`). Patterns marked **[playbook]**
> are carried over verbatim from there; that doc holds the long-form rationale,
> incident history, and the sections this site hasn't grown into yet (SEO
> server injection §6–7, share-image architecture §9, thumbnail pipelines §10).
> When this site adopts one of those sections, port its rules here and delete
> the pointer.

## 1. Architecture

| Concern | Approach |
|---|---|
| Framework | React 18, functional components only, hooks only **[playbook]** |
| Build | Vite 5 (`@vitejs/plugin-react`), `root: 'web'`, output to repo-root `dist/` **[playbook]** |
| Language | TypeScript strict (`web/tsconfig.json`); `npm run typecheck` checks web AND the sync/server code |
| Routing | Custom SPA router (`web/src/router.ts`) — real URL **paths**, `pushState` + `popstate`. No React Router, never hash routing **[playbook]** |
| State | `useState` / `useReducer` + prop drilling. No global store, no context for state **[playbook]** |
| Styling | One CSS file (`web/src/styles.css`). No CSS modules, no Tailwind, no styled-components **[playbook]** |
| Data | JSON imported directly at build time (`import dollsJson from '../../data/dolls.json'`). All game data runs **entirely client-side** — no data fetch **[playbook]** |
| Data origin | Postgres, filled by the dandegate sync (`npm run sync`). The sync step **exports** the committed `data/*.json` artifacts the web imports — the DB is the source of truth, the JSONs are build inputs (see §8) |
| Code splitting | Every page is a `lazy()` route chunk; React is its own `manualChunks` framework chunk **[playbook]** |
| SEO / embeds | Phase 1: static `index.html` baseline + client head sync. Phase 2 adopts the playbook's server-injection surface (§6 below) |
| Infographics | NONE yet — owner decision pending. When they arrive, port playbook §9 (platform-free renderers, fonts-before-draw, content-addressed URLs) before writing the first renderer |
| Images | CDN URLs (`cdn.dandegate.net`) with `loading="lazy"` + `?` placeholder; the playbook's thumbnail-tier pipeline (§10) arrives with real assets |

## 2. TypeScript conventions **[playbook]**

### Imports

```ts
// React — named imports, type-only for event types
import { useEffect, useState, useMemo } from 'react';
import type { MouseEvent, ReactNode } from 'react';

// JSON data — default import with a two-step cast
import dollsJson from '../../data/dolls.json';
const data = dollsJson as unknown as DollsFile;
```

### Component signatures

```ts
// Named exports ONLY (never default). Props typed inline or via interface.
export function ComponentName({ prop1, prop2 }: { prop1: string; prop2?: number }) { ... }
```

Lazy pages adapt at the import site, not by adding default exports:

```ts
const CharactersPage = lazy(() =>
  import('./CharactersPage').then((m) => ({ default: m.CharactersPage }))
);
```

### Typing patterns **[playbook]**

- Union types for finite sets: `type Route = 'characters' | 'character' | …`
- `as const` for fixed arrays/tuples (filter option lists)
- `Record` types for lookups (`PHASE_COLORS`, label maps)
- Discriminated unions for result state

### Custom hooks **[playbook]**

`useXxx` naming. Exported hooks are shared infrastructure (the filter hook is
THE example — §5); internal ones stay file-local.

### Comments **[playbook]**

Extensive and explanatory: WHY decisions were made, invariants, edge cases,
cross-references. The filter module's OR-within-row / AND-across-rows
semantics is exactly the kind of rule that gets a comment.

## 3. Styling — one CSS file, token-driven **[playbook]**

Everything lives in `web/src/styles.css`. Do not add a second CSS file, CSS
modules, Tailwind, or styled-components. New feature styles go under a
`/* ---- Feature ---- */` banner with a shared class prefix.

### Design tokens (identical to nikke-sim — owner decision 2026-08-15)

```css
:root {
  color-scheme: dark;
  --bg: #101216;        /* page background */
  --panel: #181b22;     /* card/panel background */
  --panel2: #1f232d;    /* elevated/sunken surface (inputs, alternate rows) */
  --border: #2a2f3b;    /* borders, dividers */
  --text: #e7eaf0;      /* primary text */
  --muted: #8b93a3;     /* secondary text, labels, placeholders */
  --accent: #5b9dff;    /* interactive blue (buttons, active states, links) */
  --warn: #e0b04b;      /* warning/caution yellow */
}
```

All colors reference these tokens. Game-phase accent colors (GFL2's analog of
nikke-sim's `ELEMENT_COLORS`) live in a TS const when first needed — see the
scaffolding plan §6 for the proposed `PHASE_COLORS` values.

### Fonts

System stack only (`14px/1.5 -apple-system, BlinkMacSystemFont, 'Segoe UI',
Roboto, sans-serif`). **No self-hosted font files yet**: nikke-sim's Roboto
subset pipeline exists for canvas/browser pixel-parity in infographics, and
this site has no infographics. When they arrive, port playbook §3's font rules
(subsets, `unicode-range`, `ensureRoboto`) together with the renderers.

### Typography, spacing, radius, shadows **[playbook]**

- Base 14px · h1 22–28px · h2 15–18px · labels 11px uppercase muted ·
  `tabular-nums` on numeric columns
- 2px-based spacing scale; card padding 10–16px; page padding
  `24px 20px 60px` desktop / `14px 8px 48px` mobile
- Radius: pills 999px · cards 10px · modals 12px · inputs/buttons 8px ·
  portraits 6–8px
- Shadows always dark and subtle (`0 8px 24px rgba(0,0,0,.5)` dropdowns,
  `0 12px 40px` modals)

### Layout, buttons, inputs, tables **[playbook]**

`.app` page container (max-width 1180px); `.card` panel pattern; three button
voices (pill toggle with `.on`, primary action, outlined); inputs on `panel2`
with `border` + 8px radius; collapse tables with uppercase muted headers.

### Responsive breakpoints **[playbook]**

900 / 760 / 720 / 640px as in the playbook; 640 is the main mobile breakpoint
(nav → dropdown). Prefer content-aware layout (`ResizeObserver`) over
breakpoints; never `window.addEventListener('resize')`.

### Accessibility baselines (site-wide, in styles.css) **[playbook]**

```css
:focus-visible { outline: 2px solid var(--accent); outline-offset: 2px; }
@media (prefers-reduced-motion: reduce) { /* kill animations/transitions */ }
```

Icon-only controls carry `aria-label` + `.sr-only` text twin; filter toggles
use `aria-pressed`; panels use `role="menu"`/`role="alertdialog"` where the
playbook does.

## 4. Routing and navigation **[playbook]**

Every view is addressed by a real URL **path** (never a hash) — paths reach the
server and are independently crawlable.

### Route model (`web/src/router.ts`)

- `Route` union: `home | characters | character | weapons | weapon |
  team-builder | credits`.
- Parameterized routes (`/characters/<slug>`, `/weapons/<slug>`) are excluded
  from the flat `ROUTES` list — `hrefFor('character')` would produce a
  slug-less dead end. Detail routes are detected by a present second segment.
- `navigate()` = pushState + synthetic popstate; `useRouteAndSlug()` is the
  single subscription route and slug derive from; scroll-to-top only when the
  route actually changes.

### Links are real anchors, intercepted **[playbook]**

```tsx
<a href={href} onClick={onSpaLinkClick(href)} className={current === route ? 'on' : ''}>
```

Modified clicks (⌘/middle) behave natively. Render real `href`s always —
crawlability and middle-click depend on it. The `/characters` and `/weapons`
grids are navigation-mode card grids precisely so every card is a crawler-
followable `<a>`.

## 5. Component patterns

### The filter module (`web/src/components/DollGrid.tsx`)

The central shared component, structurally identical to nikke-sim's
`CharacterGrid.tsx` split:

| Export | Role |
|---|---|
| `useDollFilter({ exclude?, restrict? })` | owns ALL filter/search state + the derived doll list + any thumbnail maps. Split from rendering so a caller can place controls and grid separately (the Team Builder puts filters above the squad strip) |
| `DollFilters` | `<details>` panel + search box + "Showing N of M" + Clear all. `defaultOpen`: true on `/team-builder`, false on `/characters` |
| `DollCards` | the grid. **Navigation mode** (`linkFor` → whole card is an `<a>`) vs **badge mode** (click = place in squad; separate corner profile link) |

Filter semantics (binding, from the playbook): **OR within a row, AND across
rows**; an empty row is inactive (all values pass); text search matches name
and `searchTags` aliases. Filter rows: Class, Phase, Ammo, Weapon type
(icon-capable rows) + Rarity (text pills) — vocabulary defined as
`{ id, label, icon? }` option arrays so icon assets drop in later without a
code change.

The rule that makes this worth having: `/characters` and `/team-builder` use
the SAME hook instance shape, so the filter vocabulary can never drift between
the two pages.

### Page structure **[playbook]**

```tsx
export function SomePage() {
  return (
    <div className="app page-class">
      <header>
        <h1>Page title</h1>
        <p className="muted">Introductory text…</p>
      </header>
      <section>{/* content */}</section>
    </div>
  );
}
```

Detail pages (DollPage, WeaponPage) derive EVERYTHING from the committed
`data/*.json` — never hand-write per-entity blurbs — and **degrade, never
vanish**: a section without data says so in one muted line instead of
disappearing.

### Dropdown/modal dismiss pattern (site-wide) **[playbook]**

Outside-`mousedown` + `Escape`, attached while open, cleaned up on close —
identical shape everywhere a popover exists.

### Portrait/image `<img>` pattern (current phase)

```tsx
<img src={doll.avatarUrl} alt={doll.name} loading="lazy" />
```

with the `.portrait-empty` `?` placeholder when the URL is missing. No
thumbnail tiers yet — the playbook §10 pipeline (stepped-halving downscale,
build-time tiers, one crop constant) is adopted when real art assets land. Do
NOT port it speculatively.

## 6. SEO and social embeds

**Phase 1 (now):** the static `index.html` baseline (title/description/
keywords/canonical/OG 1200×630/twitter/theme-color/WebApplication JSON-LD) +
`useDocumentHead.ts` per-route client sync (one `META` table, `{title,
description}` per route key; detail pages set their own head via the
UnitPage-style `setMeta`/`setOg`/`setCanonical` helpers so the full dataset
never lands in the eager entry chunk).

**Phase 2 (at first deploy):** port playbook §6–7 in full — Hono static
server with per-route `TAB_META` injection (no user-agent sniffing), no-JS
bodies for `/characters` + detail pages generated from the SAME `data/*.json`
the pages read, hard 404s for unknown routes, cache policy, robots.txt with
named social-crawler groups + AI allowlist, generated sitemap + drift test,
llms.txt. The playbook's lockstep rule applies from that day: route meta lives
in ALL tables at once, never fewer.

Canonical convention **[playbook]**: lowercase path, no trailing slash except
root.

### JSON-LD **[playbook]**

- Static `WebApplication` in index.html
- `/characters` + `/weapons`: `CollectionPage`
- Doll/weapon detail pages: `WebPage` with `about`
- Escape via `escapeJsonLd` (prevents `</script>` breakout)

## 7. Backend and data flow

### The rule **[playbook]**

All game data runs client-side. The ONLY data the app reads at runtime is
build-imported JSON. **Never add a `fetch()` for game data.**

### The GFL2 hop

Game data is owned by Postgres (dandegate sync). The sync step exports the
four committed artifacts the web imports — `data/dolls.json`,
`data/weapons.json`, `data/keys.json`, `data/effects.json`. Fresh checkouts
build from the committed JSONs without a DB. After any sync that adds dolls
or weapons, the exporter rewrites the JSONs and the next build picks the new
entities up automatically.

### Cross-references inside the data

- Doll ↔ weapon imprint: by weapon `id`
- Keys/effects ↔ doll: by `dollId`
- `[effect:<uuid>]` markers inside skill/weapon text: resolved against
  `effects.json` (id → effectName) through ONE helper in `data.ts` — never
  ad-hoc regexes at call sites
- Slugs ↔ ids: the exporter guarantees slug uniqueness (§4.3 of the plan);
  `data.ts` owns the lookup

### No user-data backend yet

There is no auth/profiles API on day one. When squad save/share is built,
port the playbook §8.2 shape (single `auth.ts` client, bearer token in
localStorage delivered via URL fragment, bakery-bot's kind-keyed profiles API
with a new kind slug) — do not invent a second pattern.

## 8. Naming conventions **[playbook]**

| Thing | Convention | Examples |
|---|---|---|
| Components | PascalCase, named export | `DollFilters`, `DollCards` |
| Hooks | camelCase, `use` prefix | `useDollFilter`, `useWeaponFilter` |
| CSS classes | kebab-case, semantic, shared prefix per feature | `.dollcard-*`, `.teambuilder-*` |
| Constants | UPPER_SNAKE or camelCase const | `PHASE_COLORS`, `CLASS_OPTIONS` |
| Types | PascalCase | `Route`, `Doll`, `FilterState` |
| Data modules | kebab-case | `data.ts` (the typed JSON layer) |
| Page files | PascalCase + `Page` suffix | `CharactersPage.tsx`, `DollPage.tsx` |

## 9. Do / Don't **[playbook, adapted]**

### Do

- Use `var(--token)` for every color
- `loading="lazy"` on grid images; `tabular-nums` on numeric columns
- Named exports; `as const` for fixed arrays; explanatory WHY comments
- Route new pages through `lazy()` + Suspense
- Degrade, never vanish — missing data gets one muted line
- Resolve `[effect:uuid]` markers through the shared `data.ts` helper
- Keep both regions: `regionTag` travels with every entity to the UI (badge),
  never silently dropped

### Don't

- No CSS modules / Tailwind / styled-components; no second CSS file
- No default exports; no state library; no React Router; no hash routes
- No `window.addEventListener('resize')`
- No `fetch()` for game data; no runtime DB/API access from `web/`
- No hand-written per-entity blurbs — everything derives from `data/*.json`
- No hand-editing `data/*.json` — they are sync output
- No font files until infographics exist (§3)
- No thumbnail/downscale pipeline until real art exists (§5)
- `as any` only for JSON-import casts

## 10. Recipes

### Adding a new page **[playbook]**

1. `web/src/YourPage.tsx` — `<div className="app page-class">` + header
2. `router.ts` — add to `Route` (+ `ROUTES` if not parameterized) + path
   mapping
3. `main.tsx` — `lazy()` import + a branch in the route switch
4. `SiteChrome.tsx` — nav or hamburger entry
5. `styles.css` — a `/* ---- Your page ---- */` section, shared class prefix
6. `useDocumentHead.ts` — a `META` entry (unique keyword-rich title)
7. JSON-LD if the page has structure worth declaring (§6)
8. Phase 2+: server `TAB_META` + sitemap entry + no-JS body if indexable

### Adding a filter axis

1. Option array in `DollGrid.tsx` (`{ id, label, icon? }`, `as const`)
2. State + toggle in `useDollFilter`; predicate inside the `useMemo` filter
   (OR within the row, AND with the others)
3. A `FilterRow` in `DollFilters`; icon file into `public/gfl2-icons/` if
   available (pill fallback is automatic)
4. Include the new set in `anyActive` / `clearAll`

### After a sync adds dolls/weapons

`npm run sync` rewrites `data/*.json`; commit the diff. Grids, detail pages,
and (phase 2) sitemap entries pick new entities up at the next build.
